# Спецификация: одинаковый OCR для Telegram и MAX

## Задача

Telegram обрабатывает паспорта не по тому OCR-маршруту, что MAX: OpenRouter не включён в Telegram, поэтому распознавание и заполнение пустых полей отличаются. По журналам также нельзя сразу понять, какой бот пишет сообщение и какие OCR-модули заполняли запись.

## Решение

Оба бота получают одинаковый приоритет `openrouter,rupasportread` и один и тот же OpenRouter ключ из общей конфигурации. OpenRouter распознаёт документ первым, локальный модуль дополняет отсутствующие поля. Инициализационные сообщения безопасно помечаются названием мессенджера. В JSONB диагностических данных каждой новой записи сохраняются список запущенных OCR-модулей и источник каждого поля.

## Решения по реализации

1. Compose задаёт OCR приоритет в общей конфигурации ботов. Новый `BOT_OCR_MODULE_PRIORITY` имеет приоритет; при его отсутствии остаётся совместимость с `MAX_OCR_MODULE_PRIORITY`, затем используется hybrid значение по умолчанию. Это уравнивает процессы и не ломает текущий `.env`.
2. OpenRouter ключ остаётся в общем `.env`, который оба бота уже читают. Удаляется telegram-only пустое значение, затирающее ключ. Значение ключа не печатается; логируется только безопасный статус включения.
3. Для новых строк метаданные записываются в имеющееся JSONB поле `raw_payload` как `modules_used` и `field_providers`. Новая схема не нужна; историческим записям не приписываются несуществующие сведения.
4. Список модулей сохраняет порядок приоритета, а `field_providers` отмечает модуль-поставщик или `inferred` для выведенного значения. В базу не попадают исходные ответы OpenRouter или распознанные строки.
5. Деплой обновляет только два bot-сервиса. PostgreSQL volume не удаляется; миграция не изменяется и не требуется.
6. Оба entry point настраивают структурное логирование с контекстом `messenger=telegram|max` до старта polling. Инициализационное сообщение может указывать только известные имена OCR-модулей и факт настройки ключа, но не произвольные значения окружения или сам ключ.

## Границы и швы

| Модуль | Владеет | Выставляет | Прячет |
|---|---|---|---|
| Общая конфигурация Compose | переменными среды общих контейнеров и совместимостью приоритетов | одинаковые `OCR_MODULE_PRIORITY` и общие секреты из `.env` | различия OCR-конфигурации между мессенджерами |
| Entry point + structured logger | стартовыми сообщениями процесса и полем `messenger` | `setup_logger(log_level, messenger_source=...)` и безопасные сведения конфигурации | секреты, содержимое документа, полный ответ провайдера |
| Hybrid OCR | порядком модулей и происхождением полей | `modules_used` и `field_providers` в результате распознавания | детали ответа провайдера для persistence |
| Passport processing + repository | диагностической JSONB-структурой записи | `raw_payload` с двумя полями диагностики | сырой OCR/API payload и данные изображения |

Швы для проверок: разрешение общей конфигурации в Compose; `setup_logger` в каждом entry point; `PassportProcessingService.process_image` и существующий вызов `PassportRepository.create`.

## Вне рамок

Новых пользовательских функций, новых провайдеров и обратного заполнения метаданных для старых записей не добавляем. Текущий запрос не содержит таких требований; для старых записей источник полей восстановить нельзя.
