# Спецификация: проверка OCR паспортов через OpenRouter

## Задача

В текущем запуске MAX-бота фотографии доходили до OCR, но локальный распознаватель не извлекал паспортные данные. Нужно включить выбранный пользователем OpenRouter/Qwen и проверить, решает ли он проблему на предоставленных тестовых снимках.

## Решение

Использовать имеющийся `OpenRouterProvider` и общий `PassportProcessingService`, не добавляя второй OCR pipeline. Выбранная модель — `qwen/qwen2.5-vl-72b-instruct`. OpenRouter является первым провайдером только в MAX; `rupasportread` остаётся его локальным резервным/дополняющим распознавателем. Telegram сохраняет текущий OCR-приоритет и не получает OpenRouter API key.

Секрет хранится только в игнорируемом локальном `.env`; его значение не попадает в репозиторий, вывод команд и логи. Изображения тестовой папки разрешено отправить выбранному внешнему провайдеру для OCR. Тестовый прогон вызывает распознавание без `process_image`, поэтому не создаёт записей в PostgreSQL. Результаты OCR и паспортные поля не выводятся в логи и не сохраняются в файлы отчёта.

## Решения по реализации

- Настройки берутся из уже существующего `Settings` и `.env`; отдельный конфиг не создаётся.
- Базовый `OCR_MODULE_PRIORITY` в `.env` остаётся прежним для Telegram. `docker-compose.yml` задаёт `openrouter,rupasportread` только сервису MAX и убирает `OPENROUTER_API_KEY` из окружения Telegram. Для отдельной оценки Qwen тестовый вызов изолирует OpenRouter в процессе, не меняя OCR приоритет другого сервиса.
- Проверочный вызов использует существующий shared OCR service. Чтобы тестовые паспорта не попали в рабочую БД, прогон использует `recognize_image`, не сохраняющий записи; это тот же нормализующий/OCR путь без шага persistence.
- Вручную сверяются только уже видимые на изображениях тестовые поля; вывод и итоговый отчёт обезличены.
- При отсутствующем ключе, ошибке авторизации, исчерпанной квоте, timeout или ошибке модели сетевой тест останавливается безопасно. Токен, URL с credentials, ответ API и содержимое документа не печатаются.
- После подтверждённого теста перезапускается только `max_bot`; миграции не нужны, так как схема БД не меняется.

## Границы и швы

| Модуль | Владеет | Выставляет | Прячет |

Тестовые швы: существующий `PassportProcessingService.recognize_image` и `docker compose` service `max_bot`.

## Принятые допущения

- **A01 → R01:** тест не создаёт записей паспортов в рабочей PostgreSQL; используется существующий `recognize_image`, который проходит через общий нормализующий/OCR путь без persistence.
- **A02 → G03:** считать результат достаточно точным для перезапуска, если номер документа и дата рождения прочитаны без ошибок на каждом тестовом снимке, а точность остальных видимых полей вместе не ниже 90%. Порог выбран консервативно из-за чувствительности паспортных данных.
- **A03 → R03:** после исправления перезапустить только `max_bot`, сохранив независимый Telegram-сервис и общую PostgreSQL; миграция не запускается, если схема не менялась.
- **A04 → R02:** если включение OpenRouter не устраняет сбой, продолжить диагностику текущего pipeline и исправить подтверждённую причину, не ограничиваясь конфигурацией.
- **A05 → G03:** в логах и отчёте показывать только обезличенные метрики, не сами изображения, поля паспорта, ответы модели или секреты.
- **A06 → G02:** ключ OpenRouter и его приоритет доступны только MAX-контейнеру; Telegram продолжает использовать текущую конфигурацию OCR.
- **A07 → R02:** новая копия проекта и отдельная бизнес-логика не создаются; используются существующие shared OCR/provider boundaries.

## Деплой и эксплуатация

- Закоммитить и отправить текущий код и проектную документацию в настроенную ветку `main`. Локальный `.env` и секреты не входят в commit.
- Репозиторий `mchomak/pasport_scan` публичный, поэтому изображения из локальной папки `pasports_test` остаются на машине пользователя и исключаются из Git и Docker build context.
- Развернуть только `max_bot` в `/opt/passport-scan`, с `BOT_VARIANT=full` и приоритетом `openrouter,rupasportread`. PostgreSQL и миграция запускаются через зависимости Compose; Telegram-сервис не запускается.
- Подготовить `.env` на сервере без секретов и не запускать контейнеры до ручного заполнения пользователем `MAX_BOT_TOKEN`, `OPENROUTER_API_KEY`, `ADMIN_IDS`, `POSTGRES_PASSWORD` и согласованного `DATABASE_URL`. Модель по умолчанию для этого запуска — `qwen/qwen2.5-vl-72b-instruct`.
- До установки контейнера сохранить снимок слушающих TCP/UDP-сокетов `ss -lntup` и статусы VPN-контейнеров `amnezia-xray` и `amnezia-awg2`; после запуска убедиться, что контейнеры остались активны, исходные слушающие сокеты не изменились, а `443/tcp`, `443/udp` и `585/udp` по-прежнему слушаются. MAX работает через исходящие запросы и не публикует порт; Compose не должен добавлять новых host-портов. Серверная проверка сокетов не заменяет подтверждение соединения VPN-клиентом пользователя.
- Сквозной критерий VPN: повторить после запуска тот же внешний запрос/сайт через уже настроенный клиентский VPN-профиль, который работал до запуска, и зафиксировать успех или отказ. Если у исполнителя нет клиентского профиля, состояние туннеля считается непроверенным сквозным образом; в отчёте это явно отделяется от подтверждённых контейнеров и серверных портов.
- Защитить VPN ресурсными лимитами для `max_bot`: не более одного CPU и 768 MiB памяти. Эти лимиты оставляют второй CPU доступным VPN и ограничивают ущерб от всплеска локального OCR; при превышении лимита бот может перезапуститься, что должно быть видно в итоговом отчёте.
- Одна команда запуска после заполнения `.env` поднимает `max_bot` с PostgreSQL и миграцией и запускает 24-часовой сборщик. Он снимает метрики каждые 10 секунд: нагрузку/память/диск хоста, CPU/RAM/сетевой ввод-вывод контейнеров, а также CPU и RSS процессов с именем `tesseract`. Данные не содержат командных аргументов, OCR-ответов, изображений или полей паспорта; через 24 часа сборщик завершает работу и формирует агрегированный отчёт.
- Достаточность оценивается по фактической памяти и CPU процесса Tesseract, нагрузке `max_bot`, свободной памяти и состоянию VPN. Для OpenRouter-only использовать контрольный профиль `MAX_OCR_MODULE_PRIORITY=openrouter`; для штатной проверки — `openrouter,rupasportread`. Отчёт должен отдельно указать исходные характеристики сервера (2 vCPU, около 1.9 GiB RAM), фактические пики/средние за сутки и оговорку, что без контрольного периода OpenRouter-only нагрузка Tesseract оценивается по его процессным метрикам, а не как причинно доказанная разница двух параллельных прогонов.
- После ручного запуска проверить, что `max_bot` и PostgreSQL в ожидаемом состоянии, миграция завершилась с кодом 0, не растёт `RestartCount`, портовые снимки совпадают и VPN-контейнеры активны. Команды для пользователя: `ssh root@<адрес из переписки>`, `cd /opt/passport-scan`, `nano .env`, затем `./ops/start_max_bot.sh`; секретные значения вводятся только пользователем.
