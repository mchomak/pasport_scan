У меня уже есть полностью рабочий Python-проект Telegram-бота для OCR фотографий паспортов. Бот запущен на сервере через Docker и использует PostgreSQL.

Нужно добавить поддержку российского мессенджера MAX так, чтобы Telegram-бот продолжил работать без изменений для пользователей, а MAX-бот работал параллельно и использовал ту же бизнес-логику.

Для MAX использовать Python-библиотеку `maxapi`.

Главный приоритет — НЕ создавать отдельную копию существующего проекта и НЕ дублировать бизнес-логику. Максимально переиспользуй существующий код.

Сначала внимательно изучи весь репозиторий:

- текущую структуру проекта;
- Telegram handlers;
- OCR-код;
- работу с фотографиями;
- бизнес-логику;
- PostgreSQL-модели;
- конфигурацию;
- `.env`;
- зависимости;
- Dockerfile;
- docker-compose.yml / compose.yaml, если он существует;
- миграции Alembic, если они используются;
- текущую точку запуска Telegram-бота.

После анализа самостоятельно выбери минимально инвазивную архитектуру.

## Целевая архитектура

Нужно прийти примерно к следующему разделению:
```text
Telegram adapter ──┐
                   │
                   ├── shared OCR/business layer ── shared PostgreSQL
                   │
MAX adapter ───────┘
```

Telegram и MAX должны отвечать только за messenger-specific вещи:

- получение сообщения;
- получение фотографии;
- скачивание файла;
- получение user/chat/message IDs;
- отправку ответа;
- обработку специфичных для платформы событий.

Вся логика:

- OCR;
- обработка паспорта;
- распознавание данных;
- нормализация;
- валидация;
- сохранение результата;
- форматирование результата, если возможно;
- обработка бизнес-правил;

должна быть общей.

Не копируй существующие функции Telegram-бота в MAX-бот, если их можно вынести в общий service/core слой.

Если текущая архитектура смешивает Telegram handlers и OCR-бизнес-логику, аккуратно проведи небольшой рефакторинг, не меняя существующее поведение Telegram-бота.

## MAX Bot

Добавь MAX-бота на `maxapi`.

MAX-бот должен поддерживать основной существующий пользовательский сценарий Telegram-бота:

1. Пользователь отправляет фотографию паспорта.
2. Также пользователь может переслать в бота сообщение с фотографией паспорта из другого MAX-чата.
3. Бот получает изображение.
4. Изображение передаётся в существующую OCR/business logic.
5. Результат сохраняется в общую PostgreSQL.
6. Бот отправляет пользователю такой же или максимально эквивалентный результат, как Telegram-бот.

Обязательно проверь структуру событий `maxapi` и корректно реализуй получение изображения как:

- из обычного сообщения с image attachment;
- из пересланного сообщения с изображением.

Не привязывай OCR-core непосредственно к объектам Telegram или MAX SDK.

Лучше привести входящие изображения к собственной общей структуре/интерфейсу, например:
```python
class IncomingImage:
    content: bytes
    filename: str | None
    source: MessengerSource
    external_user_id: str | None
    external_chat_id: str | None
    external_message_id: str | None
```

Название и реализацию можешь выбрать лучше, исходя из существующего проекта.

## Messenger source

Добавь понятие источника сообщения.

Например:
```python
class MessengerSource(str, Enum):
    TELEGRAM = "telegram"
    MAX = "max"
```

Не размазывай строки `"telegram"` и `"max"` по всему проекту, если можно централизовать это через Enum/константы.

## PostgreSQL

PostgreSQL должна оставаться общей для обоих ботов.

В таблицу/модель, где сохраняется результат обработки паспорта или соответствующая OCR-запись, добавь поле:
```text
source / messenger / platform
```

Со значениями:
```text
telegram
max
```

Выбери название, лучше соответствующее существующей модели.

Для существующих записей из Telegram должно быть безопасное значение:
```text
telegram
```

Если используется Alembic — создай нормальную миграцию.

Не удаляй существующие данные.

Обрати внимание на внешние идентификаторы.

Если сейчас в БД сохраняются:
```text
user_id
chat_id
message_id
```

не считай их глобально уникальными между Telegram и MAX.

Там, где требуется уникальность, она должна учитывать платформу, например концептуально:
```text
(source, external_user_id)
(source, external_chat_id)
(source, external_message_id)
```

Но не добавляй лишние constraints без необходимости — сначала изучи существующую модель и выбери наиболее безопасное решение.

Если Telegram IDs сейчас INTEGER/BIGINT, проверь, подходит ли тип для MAX. При необходимости унифицируй внешние ID через строковое представление, но не делай опасную миграцию без необходимости.

## Docker

Сейчас Telegram-бот запускается через Docker.

Нужно, чтобы после деплоя одновременно работали:
```text
telegram bot
MAX bot
```

Предпочтительная архитектура:
```yaml
services:
  telegram_bot:
    build: .
    command: <telegram entrypoint>

  max_bot:
    build: .
    command: <max entrypoint>
```

Оба сервиса:

- используют один Docker image;
- используют один код;
- получают `.env`;
- подключаются к одной PostgreSQL;
- не содержат копий OCR/business logic.

Если уже используется `docker-compose.yml` или `compose.yaml`, реализуй именно так.

Не запускай два long-running bot процесса внутри одного Docker-контейнера через:
```bash
python telegram_bot.py & python max_bot.py
```

если этого можно избежать.

Один контейнер = один основной процесс.

Dockerfile должен остаться универсальным для обоих сервисов.

Если Docker Compose в проекте сейчас отсутствует, изучи существующий способ запуска и выбери наиболее минимальное и production-friendly решение. При необходимости добавь compose, но не ломай текущую схему деплоя.

PostgreSQL не должна дублироваться — оба bot services должны использовать одну существующую БД.

## Форматирование ответа

Если текущая функция формирования результата Telegram использует Telegram-specific Markdown/HTML, отдели данные результата от platform-specific presentation.

Например:
```text
OCR result
    ↓
common result formatter
    ↓
Telegram sender
MAX sender
```

Если можно использовать один и тот же текст для обоих мессенджеров — используй один.

## Ошибки

Поведение MAX-бота должно быть эквивалентно Telegram-боту.

Обработай как минимум:

- сообщение без фотографии;
- неподдерживаемое вложение;
- несколько фотографий;
- ошибка скачивания изображения;
- timeout;
- слишком большой файл;
- ошибка OCR;
- OCR ничего не распознал;
- ошибка PostgreSQL;
- исключение API MAX.

Не допускай падения bot process из-за одного плохого сообщения.

Используй существующий logging проекта.

## Персональные данные

Бот работает с фотографиями паспортов.

Поэтому:

- не логируй содержимое изображения;
- не логируй Base64;
- не логируй секретные токены;
- по возможности не логируй полный URL изображения MAX, если он содержит временные credentials;
- не сохраняй фотографию паспорта на диск дольше, чем это требуется OCR;
- временные файлы гарантированно удаляй;
- не добавляй паспортные данные в debug-логи;
- не выводи MAX_BOT_TOKEN в startup logs.

Сохрани текущее поведение проекта относительно хранения изображений, если оно уже специально реализовано, но не ухудшай безопасность.

## HTTP/download

Если изображение MAX скачивается по URL:

- используй существующую async HTTP-инфраструктуру проекта, если она есть;
- не создавай новый `aiohttp.ClientSession` на каждое сообщение без необходимости;
- установи разумный timeout;
- проверяй HTTP status;
- ограничивай размер скачиваемого файла;
- корректно закрывай клиент при shutdown.
